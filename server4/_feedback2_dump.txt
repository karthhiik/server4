1. Executive Summary
This document provides a comprehensive, research-backed review of Plan v2: Multi-Target Slide Generation + Real-Time IR-Driven Editing. The review draws on deep analysis of four competitive reference platforms (Dokie.ai, Chronicle HQ, Canva Pro, Figma Slides), extensive GitHub open-source repository research, and a thorough investigation of adaptive learning and self-improving AI systems applicable to presentation generation. The goal is not merely to validate the existing plan but to identify critical architectural gaps, propose concrete improvements, and introduce the adaptive learning and web search template capabilities that the user has specifically requested.
Plan v2 is architecturally sound in its core thesis: a single writer emitting Node Graph IR, fanning out to four render targets, with a deck-level design system constraining visual coherence. The IR-patch edit protocol is genuinely innovative and creates a defensible moat against competitors. However, our analysis reveals several critical gaps that, if unaddressed, will prevent the system from achieving its stated ambition of surpassing Dokie.ai, Chronicle HQ, Canva Pro, and Figma Slides in design quality and professional output.
The three most significant gaps are: (1) the complete absence of an adaptive learning loop that would enable the system to improve its slide generation quality based on user feedback and behavioral signals, which is a genuine market differentiator since no competitor currently implements this; (2) the lack of a RAG (Retrieval-Augmented Generation) and web search integration layer that would enable real-time content enrichment and template auto-discovery from the web; and (3) the rendering architecture relying on DOM-based iframe rendering rather than a GPU-accelerated pipeline, which fundamentally limits the visual fidelity ceiling compared to Figma's WebAssembly/WebGPU approach and Canva's WebGL engine.
This document proposes a comprehensive adaptive learning architecture based on the MAPE-K (Monitor-Analyze-Plan-Execute-Knowledge) data flywheel pattern, contextual bandits for template selection, preference learning via DPO (Direct Preference Optimization), and a quality scoring engine inspired by the SlideAudit research framework. Additionally, we propose a RAG pipeline for content grounding, web search templates for dynamic content enrichment, and a phased GPU rendering migration path that would bring the system's visual fidelity to parity with Figma and Canva while surpassing them in AI-driven design intelligence.
2. Competitive Landscape Deep Analysis
Understanding the competitive landscape is essential for identifying where Plan v2's architecture creates genuine differentiation versus where it merely achieves feature parity. This section analyzes four reference platforms across technical architecture, design capabilities, and user experience dimensions, drawing on direct platform analysis, engineering blog posts, and user feedback from multiple review sources.
2.1 Dokie.ai: The Business-Structured Generator
Dokie.ai positions itself as an 'AI Presentation Agent' with a 'draft builder, not auto-finish' philosophy. Its core strength lies in generating structured, business-appropriate slides rather than flashy or overly designed outputs. The platform supports multi-format input including PDF-to-slides, Word-to-PPT, Excel-to-slides, URL-to-slides, and image-to-presentation, making it exceptionally versatile for business users who need to transform existing content into presentation format. Dokie.ai's PPT export quality is notably strong, with users reporting clean and fully editable outputs in PowerPoint and Google Slides.
However, Dokie.ai has significant limitations: it offers limited design customization within the tool itself, no interactive or motion elements, no custom rendering engine (standard DOM-based rendering), and limited template variety compared to Canva. The platform focuses on static PPT-compatible output and defers all animation capabilities to PowerPoint/Google Slides after export. Its pricing is competitive at approximately $12/month for Pro, with a generous free tier of 400 credits. Users appreciate the structured, clean output that 'actually feels like real business slides,' but criticize the limited design customization and the need for post-export polish for high-stakes presentations.
Key Architecture Insight:
Dokie.ai demonstrates that structured content generation with clean business formatting has strong market demand. Its multi-format input capability is a feature gap in Plan v2 that should be addressed. The lesson is that content quality and structural correctness matter as much as visual polish for business users.
2.2 Chronicle HQ: The Interactive Storyteller
Chronicle HQ, positioned as the 'Cursor for Slides,' takes a story-first, narrative-driven approach to presentation generation. It achieved Product Hunt #1 in June 2025 and represents the most innovative competitor in terms of interactive presentation capabilities. Chronicle's standout feature is its 'motion-ready widgets' - pre-built interactive components with pixel-perfect design, built-in interactivity, hover effects, animated charts, and embedded videos. This is a genuinely unique capability in the market that eliminates 'PowerPoint's static limitations' and represents a key differentiator that Plan v2 must match or surpass.
Chronicle uses a custom interactive rendering engine (likely DOM + Canvas hybrid) for its widgets and motion effects. Slides are designed to be presented live from Chronicle rather than exported, which changes the product philosophy from 'generate-and-export' to 'generate-and-present.' The platform supports real-time collaboration with shared workspaces, theme swapping across entire decks, and a token-based AI system where each AI feature consumes tokens. Pricing ranges from Free (50 tokens/month) to $12/month Pro (250 tokens) to $30/month Business (750 tokens per user).
The token-based pricing model is controversial and creates user anxiety around usage ceilings, unlike flat-rate competitors like Canva at $13/month. Additionally, PPT export is not fully available yet (rolling out through 2026), which is a major gap for enterprise workflows. Users love the clean aesthetic, interactive widgets, and story-first approach, but hate the token pricing model, limited offline capability, and fewer templates than Canva.
Key Architecture Insight:
Chronicle's interactive widgets represent a paradigm shift from static slides to interactive presentations. Plan v2's custom presentation engine (Phase 5) must support interactive elements (hover effects, animated charts, embedded videos) as first-class citizens, not just static layouts with CSS animations. The Node Graph IR should include an 'interactive' node type that maps to interactive widget rendering across all four targets.
2.3 Canva Pro: The All-in-One Design Platform
Canva represents the most mature and comprehensive platform in the competitive landscape. Its core advantage is scale: over 100,000 templates, an all-in-one platform covering presentations, social media, video, and documents, and the most comprehensive export options (PPT, PDF, MP4, web, GIF, PNG). Canva's engineering architecture is significantly more sophisticated than newer AI-only tools, using a hybrid rendering approach with C++ core compiled to WebAssembly, WebGL for GPU-accelerated rendering, and Canvas2D fallback. This gives Canva near-native performance for complex design operations.
Canva's AI features include Magic Design for Presentations (AI deck generation from descriptions), Magic Animate (one-click animation), Magic Write (AI text generation), and the upcoming Canva AI 2.0 with conversational design capabilities. The Brand Kit system is the most mature design system implementation among competitors, providing centralized brand management with colors, fonts, logos, and approved imagery stored centrally and applied automatically by AI across all designs. Canva's design tokens function as a comprehensive theming system that enforces brand consistency at scale.
However, Canva's AI-generated presentations often feel 'generic/template-y,' the platform lacks pixel-level design precision (no component-based design system like Figma), and performance issues occur with very large or complex decks. Magic Design presentations require significant manual refinement. The platform's breadth means presentations are one of many content types, not the primary focus. Pricing is highly competitive: Free tier is genuinely useful, Pro is $12.99/month, and Teams starts at $10/user/month.
Key Architecture Insight:
Canva's Brand Kit system is the gold standard for design system enforcement at team/enterprise scale. Plan v2's deck-level Design System Generator (Phase 2) should be expanded to a full Brand Kit concept that persists across decks, not just within a single deck. Additionally, Canva's C++/Wasm/WebGL rendering pipeline is technically superior to any DOM-based approach; Plan v2 should plan a GPU-accelerated rendering migration path for the custom engine target.
2.4 Figma Slides: The Design-Tool-First Approach
Figma Slides represents the most technically ambitious rendering architecture among the competitors. Built on Figma's custom WebGL rendering engine with a C++ core compiled to WebAssembly via Emscripten, Figma Slides achieves near-native performance in the browser. Figma has also announced a migration to WebGPU for even better performance. Their rendering pipeline is NOT DOM-based and NOT Canvas 2D API - it is a custom 2D vector rendering pipeline on GPU, which is industry-leading for complex document rendering. The engineering blog posts detail how this architecture was purpose-built for professional design tools.
Figma Slides offers two modes: Standard (for everyone) and Design Mode (for designers, paid), which provides full Figma Design features including Auto Layout, layers panel, advanced properties, and component reuse from Figma Design files. The AI features include deck generation from prompts, AI presenter notes, AI text tools (rewrite, translate, shorten, adjust tone), and Quick Designs for layout suggestions. The component and variable system (Figma's design token equivalent) is the most powerful among competitors for designers who need pixel-level control.
However, Figma Slides has critical export gaps: no native PPT export (a dealbreaker for enterprise workflows), no MP4/video export, and animations do not survive PDF export. The platform is online-only with no offline mode, leading to the Hacker News characterization as a 'beautiful disaster' for in-person presenting. The two-mode system (Standard/Design) creates a confusing split experience. Pricing is competitive when bundled with existing Figma subscriptions ($3-5/month add-on) but Design Mode requires a paid Figma plan.
Key Architecture Insight:
Figma's C++/Wasm/WebGL/WebGPU rendering pipeline is the technical ceiling for browser-based presentation tools. Plan v2's custom engine target should plan a Phase 11+ migration to a similar architecture. In the interim, the CSS View Transitions API + Web Animations API approach is pragmatic but will hit a visual fidelity ceiling. The two-mode approach (Standard/Design) is worth studying - Plan v2 could offer a similar split where the default editing experience is simple, but a 'Design Mode' exposes the Node Graph IR directly for power users.

3. GitHub & Open-Source Architecture References
This section catalogs the most relevant open-source repositories and architectural patterns discovered during research, providing concrete references that Plan v2's implementation should study and potentially integrate. Each reference includes the repository URL, architectural insights, and specific relevance to the Plan v2 system.
3.1 Presentation Engine Alternatives
Slidev and Marp represent the two most architecturally relevant presentation frameworks. Slidev's Markdown-as-IR approach, where Markdown + frontmatter serves as both human-writable and AI-writable intermediate format, directly parallels Plan v2's Node Graph IR concept. Their Issue #2475 discussing 'Slidev for Agents / Agents for Slides' shows the community is already thinking about agentic slide generation. Marp's layered architecture (Parser, Converter, Renderer, Exporter) with clear boundaries between stages maps directly to Plan v2's pipeline stages (Writer, Node Graph Builder, Design System Generator, Transformers). Their markdown-it plugin system for extending the parser is a model for how Plan v2's layout blueprint system should be extensible.
3.2 IR-Driven / Node-Graph UI Systems
tldraw is the single most architecturally relevant reference for Plan v2's Node Graph IR and editing system. Their Editor + Store + ShapeUtil pattern provides a proven model for how a slide editing system should work: each slide is a 'page' containing Shape records (paralleling SlideNode records), the Editor manages mutations through an undo/redo stack, and the Store provides reactive updates. Their AI agent integration pattern (the agent-template repo) shows how AI can manipulate the canvas programmatically, directly applicable to Plan v2's IR-patch edit protocol. React Flow should be the library of choice for visualizing the Node Graph IR in Phase 8's editing UI, with its useNodesState/useEdgesState hooks providing reactive state management.
3.3 Design System Generators
Style Dictionary's transform pipeline is the definitive reference for Plan v2's Phase 2 Design System Generator. The pattern of raw tokens entering a pipeline, undergoing name transforms and value transforms, and emerging as platform-specific outputs (CSS custom properties, inline styles, render-specific config) directly maps to Plan v2's design system generation flow. The registerTransform() and registerFormat() APIs enable a plugin ecosystem that Plan v2 should adopt for extensible design system generation. Theo's token resolution algorithm (where tokens can reference other tokens and the system resolves the chain) is essential for supporting theme inheritance and derived tokens in the design system.
3.4 Adaptive Learning & Slide Generation AI
PPTAgent/DeepPresenter is the most directly relevant repository for Plan v2's adaptive learning ambitions. Their two-stage architecture (content analysis + reflective editing) implements the exact pattern needed: generate a slide, observe the rendered result, and iteratively refine. The 'environment-grounded reflection' means the agent actually sees the rendered output (not just the code), which is the key insight for Plan v2's adaptive quality improvement. V2 (DeepPresenter) adds Researcher + Presenter agents coordinating via a shared observation space, which maps to Plan v2's writer + transformer pipeline with an added QA observation layer.
Auto-Slides provides the multi-agent decomposition pattern that Plan v2 should study: separate agents for content, structure, visuals, and QA. The QA agent provides the feedback loop that Plan v2 currently lacks. Presenton's template-based generation approach ensures visual consistency and their BYOK (Bring Your Own Key) model provider support is a practical pattern for Plan v2's ModelRouter. SynSlideGen's annotation pipeline could help build a training dataset of 'good slide layouts' for Plan v2's adaptive quality model, with bounding boxes, element types, and text regions as training labels.
4. Plan v2 Phase-by-Phase Deep Review
This section provides a detailed review of each phase in Plan v2, identifying specific strengths, gaps, risks, and improvement recommendations. Each phase review is grounded in the competitive analysis and open-source research presented in the preceding sections.
4.1 Phase 1: Backend IR + CompiledSlide Schema
Strengths:
The four-key artifacts dictionary is well-designed and provides clean separation of concerns.
The artifact_version field enables future real-time collaboration without rework.
The backward-compat mirror of jsx_source is pragmatic and reduces migration risk.
Gaps & Improvements:
Missing: artifacts should include an 'interactive_widgets' key for Chronicle-style interactive elements. Without this, the schema cannot represent hover effects, animated charts, or embedded videos as first-class artifacts.
Missing: A 'quality_score' field on CompiledSlide that stores the automated quality assessment from the adaptive learning system. This should be a float between 0 and 1, populated by the Quality Scoring Engine proposed in Section 5.
Missing: A 'user_feedback' sub-document that stores implicit and explicit feedback signals (edit distance, retention rate, regeneration count, explicit ratings). This is the foundation for the adaptive learning loop.
The design_system_version FK should be expanded to a full Brand Kit reference that persists across decks, not just within a single deck. Canva's Brand Kit is the competitive benchmark here.
MongoDB storage for all four artifacts will cause significant bloat (4x writes per slide). The plan mentions Brotli compression but should specify when compression happens (write-time vs read-time) and set TTL policies for unused artifacts.
4.2 Phase 2: Deck-Level Design System Generator
Strengths:
The deck-level design system is the correct architectural fix for visual coherence and is a genuine differentiator.
The DESIGN.md prompt format (YAML front matter + markdown rationale) is inspired and provides structured context to the LLM.
The deterministic CSS skeleton surviving LLM failure is excellent engineering - graceful degradation.
Caching by hash(tokens + mode + slide_count_bucket) with 7-day TTL is well-thought-out.
Gaps & Improvements:
Missing: The design system should generate interactive widget styles (.widget-hover-card, .animated-chart-bar, .embedded-video-frame) in addition to static component classes. Chronicle HQ's motion-ready widgets are the competitive benchmark.
Missing: A Brand Kit persistence layer that stores design systems across decks and enables cross-deck brand consistency. The current design only generates per-deck; Canva's Brand Kit works across all designs.
Missing: Design system versioning with diff capability - when a user tweaks the design system, the system should track what changed and propagate those changes across all slides in the deck.
The ~3-5KB CSS budget is too conservative for premium/interactive presentations. Chronicle HQ's widget styles alone exceed this. Budget should be 8-12KB for premium mode with interactive elements.
Style Dictionary's transform pipeline should be adopted here. Raw tokens should go through name transforms, value transforms, and format-specific outputs rather than a single LLM call generating all CSS directly.
4.3 Phase 3: Node Graph IR + AnimationIR
Strengths:
The Node Graph IR with geometry is the correct abstraction for enabling direct manipulation editing (Phase 8).
The AnimationIR with per-transformer deterministic mapping is excellent - a single source of truth for animation semantics.
The layout blueprints library (12 named blueprints) provides good coverage of common slide layouts.
The writer-is-not-changed constraint with a downstream transformation step is pragmatic and reduces risk.
Gaps & Improvements:
Missing: An 'interactive' node type in SlideNode for hover effects, animated charts, embedded videos, and other Chronicle-style interactive elements. The current type union (text, stat, image, shape, chart, list, quote, icon) cannot represent interactivity.
Missing: A 'responsive' property on SlideNode that defines how the element adapts to different viewport sizes. Presentations are viewed on laptops, projectors, tablets, and phones; the IR should encode responsive behavior.
Missing: A 'data_binding' property on SlideNode that links the node to a data source (API endpoint, spreadsheet cell, web search result). This is essential for the RAG/web search integration proposed in Section 6.
The 12 layout blueprints should be extensible via a plugin system inspired by Marp's markdown-it plugins. Users should be able to create custom layout blueprints that the system learns to use.
The AnimationIR should include an 'interactive_trigger' field for animations triggered by user interaction (click, hover, scroll) rather than just entry/emphasis/exit. This is essential for interactive presentation mode.
BackgroundLayers should support a 'video' type for video backgrounds, which are increasingly common in premium presentations (Chronicle HQ supports embedded videos).
The tldraw Store + Editor pattern should be adopted: each slide's NodeGraphIR should be a reactive Store that supports undo/redo, with the Editor managing mutations. This is the proven architecture for real-time editing of visual IR.
4.4 Phase 4: HTML/CSS/JS Transformer
Strengths:
The constrained polish approach (design system is read-only to the LLM) is the correct architecture for maintaining visual coherence.
The accessibility gate as a structural pipeline step (not a prompt wish) is genuinely innovative and a competitive differentiator.
The fallback chain (DeepSeek-V3.2 to GPT-4o-mini to deterministic template) provides robust degradation.
The fingerprint cache with hash(node_graph + design_system_version + animation_ir + mode) is well-designed.
Gaps & Improvements:
Missing: The transformer should also generate interactive widget HTML/CSS/JS when the Node Graph contains 'interactive' nodes. Without this, the HTML transformer cannot produce Chronicle-quality interactive elements.
Missing: A quality scoring step after the accessibility gate that evaluates the visual quality of the polished output (typography, spacing, color harmony, layout balance). This score should feed back into the adaptive learning loop.
The premium prompt's 'investor-grade designer' framing may not generalize across all premium use cases. Consider mode-specific prompts: 'investor-grade' for pitch decks, 'editorial' for reports, 'creative' for branding, 'technical' for engineering.
The 64KB/96KB size limits are appropriate for standard/premium slides but may be insufficient for interactive slides with embedded widget JavaScript. Consider a 128KB limit for interactive mode.
The lxml.html.fromstring parse check is necessary but not sufficient. Add CSS validation (tinycss2 parse), JavaScript syntax validation (esprima parse), and a visual regression test suite (golden screenshots per intent x layout).
4.5 Phase 5: Custom Presentation Engine + Reveal-Legacy
Strengths:
Building a custom engine on View Transitions API + Web Animations API + IntersectionObserver is the correct modern approach.
The GSAP fallback for Firefox and older Safari provides necessary browser compatibility.
The morph transitions via View Transitions API with data-morph-id are a genuine differentiator.
Demoting Reveal.js to legacy export-only is the right call given its limitations.
Gaps & Improvements:
Critical Gap: The custom engine is DOM-based with CSS animations. This fundamentally limits the visual fidelity ceiling compared to Figma's WebAssembly/WebGPU rendering and Canva's WebGL engine. The plan should include a Phase 11+ migration to a GPU-accelerated rendering pipeline using Canvas 2D or WebGL for the engine target.
Missing: Interactive widget rendering in the custom engine. Chronicle HQ's motion-ready widgets require a more sophisticated rendering approach than CSS animations. The engine should support Canvas-based widget rendering for interactive elements.
Missing: A 'Design Mode' concept similar to Figma Slides, where power users can directly manipulate the Node Graph IR visually. This should use tldraw's Editor + Store pattern.
The speaker view should use BroadcastChannel from MVP, not deferred to Phase 10. It is a critical feature for live presenting and relatively simple to implement.
The browser support strategy should include a feature-detection script that runs at deck load time and selects the optimal rendering path automatically, rather than requiring GSAP polyfill loading for all Firefox/Safari users.
Missing: Scroll-driven narrative mode (progressive enhancement) should be a first-class feature, not just mentioned. This is a unique differentiator that no competitor offers - the ability to scroll through a presentation like a long-form article with animated reveals.
4.6 Phase 6: Sandbox Runtime - 4 Render Targets
Strengths:
The 3-tier progressive pipeline (T1 Instant < 200ms, T2 Fast < 2s, T3 Polished < 8s) is well-designed for perceived performance.
The hot-swap UX with 200ms fade transition for T3 polish completion is a good user experience pattern.
The sandbox isolation model (outer iframe allow-same-origin, inner srcdoc allow-scripts only) is secure.
Gaps & Improvements:
The T1 < 200ms target is ambitious and may not be achievable with design-system CSS loading. The plan acknowledges this but the fallback (deterministic-only T1 without design system CSS) would look significantly different from the polished version, causing a jarring hot-swap. Consider T1 using a simplified design system (colors + fonts only, no layout classes) to minimize the visual delta.
Missing: The sandbox should support a 'Design Mode' iframe that renders the Node Graph IR visually using tldraw or React Flow, allowing power users to directly manipulate nodes and edges.
The image-patch logic patching all four artifacts on slide_image_ready should be generalized to a 'patch-all-artifacts' utility that handles any asset update, not just images. Future asset types (videos, 3D models, interactive data) will need the same treatment.
Missing: A performance monitoring layer that tracks render time per target per tier, logged to a metrics endpoint. This data feeds the adaptive learning system to optimize rendering paths over time.
4.7 Phase 7: Frontend - Intent-Based UX + Fingerprint Cache
Strengths:
The intent-based UX (Enhance/Present/Export) hiding render plumbing from users is the correct abstraction.
The Auto resolution (editing to kit_jsx, presenting to engine, exporting to html_css_js) is intuitive.
The fingerprint cache with artifact_version keying prevents unnecessary recompilation.
Gaps & Improvements:
Missing: A 'Learn' or 'Improve' intent button that triggers the adaptive learning feedback loop - 'Was this slide helpful? Rate 1-5 stars' or implicit tracking. This is the user-facing entry point for the adaptive learning system.
Missing: A 'Web Search' panel that allows users to trigger RAG-based content enrichment for their slides. This connects to the web search template system proposed in Section 6.
Missing: A 'Brand Kit' management UI where users can define and persist design systems across decks, similar to Canva's Brand Kit. The current design only generates per-deck design systems.
Missing: A 'Template Gallery' UI that showcases layout blueprints and allows users to browse, select, and save custom templates. This connects to the adaptive learning system's template mining capability.
The Advanced collapsible should include a 'Quality Score' display showing the automated quality assessment for each slide, providing transparency into the adaptive learning system's evaluation.
4.8 Phases 8-10: Post-MVP Review
Phase 8 (IR-Patch Edit Protocol) is correctly identified as the marquee differentiator. The JSON IR patch approach (LLM never outputs HTML for edits) is genuinely innovative and creates a defensible moat. However, the layout swap algorithm's semantic matching function needs more specification - how does semantic_match() resolve ambiguity when multiple nodes could match a slot? The tldraw Editor pattern should be adopted here for the state machine managing mutations.
Phase 9 (PDF + PNG Export) is table stakes but should include PPT export as well, given that Dokie.ai's strongest feature is PPT export quality and Figma Slides' biggest gap is the lack of PPT export. PPT export should be elevated from 'not mentioned' to MVP requirement. The python-pptx library can generate PPT files from the Node Graph IR with design system styling.
Phase 10 (Smoke + Cost/Latency Gate + Video Export) correctly identifies latency and cost gates as critical pre-ship requirements. The video export via MediaRecorder API is scoped appropriately as deferred. However, the cost gate targets should be validated against actual DeepSeek-V3.2 pricing at production scale, and the 8-slide-per-second semaphore may need adjustment based on real-world load testing.
5. Critical Gaps & Missing Architecture
This section identifies the three most significant architectural gaps in Plan v2 that must be addressed to achieve the stated ambition of surpassing Dokie.ai, Chronicle HQ, Canva Pro, and Figma Slides. Each gap is analyzed with competitive context, technical requirements, and proposed architecture.
5.1 Gap 1: No Adaptive Learning Loop
The most critical gap in Plan v2 is the complete absence of an adaptive learning mechanism. No phase, no data structure, and no pipeline stage captures user feedback or uses it to improve future slide generation. The system generates slides deterministically based on the writer's output, applies a design system, polishes with an LLM, and delivers the result - but it never learns whether the result was good, whether the user was satisfied, or how to do better next time. This is a fundamental architectural omission because adaptive learning is not just a 'nice-to-have' feature; it is the mechanism by which the system evolves from a fixed-output generator into a self-improving design intelligence.
The competitive landscape confirms that no competitor is currently implementing true adaptive learning from user feedback for slide design. Beautiful.ai uses hardcoded design rules (not learning), Canva does content-based personalization (not feedback-based learning), and Gamma does product-level A/B testing (not per-user learning). This represents a genuine differentiation opportunity - the first presentation tool that learns from its users' behavior to generate progressively better slides.
Research into self-improving AI systems points to the MAPE-K (Monitor-Analyze-Plan-Execute-Knowledge) data flywheel as the production pattern for adaptive systems. In this pattern, the system continuously monitors user interactions, analyzes behavioral signals to identify quality patterns, plans improvements to the generation pipeline, executes those improvements, and updates its knowledge base. The key insight is that implicit feedback signals (which slides users keep vs. edit vs. delete, how much they modify generated content, whether they regenerate) are more abundant and reliable than explicit ratings, and should be the primary training signal.
The PPTAgent/DeepPresenter repository provides the most directly relevant architecture: a reflective generation loop where the agent observes rendered output and iteratively refines. Their 'environment-grounded reflection' pattern - where the agent actually sees the rendered result, not just the code - should be adopted as the core feedback mechanism. The SlideAudit research framework (ACM 2025) provides the evaluation taxonomy: automated quality assessment across layout, typography, color, and imagery dimensions with 2,400 annotated slides as training data.
5.2 Gap 2: No Web Search / RAG Integration
Plan v2 has no mechanism for enriching slide content with real-time information from the web. The writer generates content based on the user's input prompt alone, with no access to current data, statistics, citations, or visual references. This is a significant gap because presentations are inherently time-sensitive - a pitch deck needs the latest market data, a quarterly review needs current financials, and a research presentation needs up-to-date citations. Without RAG (Retrieval-Augmented Generation) and web search integration, the system generates slides that may contain outdated or generic information.
Standard RAG architecture (vector database + re-ranking + generation) is directly applicable to slide content enrichment. A hybrid search approach combining semantic search and keyword search is most effective for finding relevant content. Web search adds 1-5 seconds of latency but dramatically improves content freshness and accuracy. The web search results should be injected into the writer's context as structured data, not raw HTML, to maintain the content-shaped IR that the downstream pipeline expects.
Beyond simple content enrichment, web search should enable 'template auto-discovery' - the ability to analyze existing presentations found on the web and extract layout patterns, color schemes, and structural templates that can be added to the system's blueprint library. This creates a self-expanding template system that grows more capable over time, learning from the best presentations available online.
5.3 Gap 3: Rendering Engine Fidelity Ceiling
Plan v2's custom presentation engine (Phase 5) is built on CSS View Transitions API + Web Animations API + IntersectionObserver, with GSAP as a fallback. While this is a pragmatic choice for the MVP timeline, it fundamentally limits the visual fidelity ceiling compared to Figma's C++/Wasm/WebGPU rendering pipeline and Canva's C++/Wasm/WebGL engine. CSS-based rendering cannot achieve the same level of pixel-perfect vector rendering, GPU-composited layer management, and complex visual effects that a custom GPU pipeline can deliver.
The practical implications are significant: CSS transitions cannot do custom shader-based transitions (dissolve, warp, particle), GPU-composited layer management is limited to what the browser's compositor supports, and complex visual effects (blur, shadows, blend modes) are slower and less precise in CSS than in a custom GPU pipeline. For the MVP, the CSS-based approach is acceptable, but the architecture should be designed with a clear migration path to GPU-accelerated rendering.
The recommended migration path is: Phase 1-7 ship with CSS-based rendering (current plan), Phase 8-9 add Canvas 2D rendering for interactive widgets (hybrid approach), Phase 11+ migrate the engine target to a WebGL/WebGPU pipeline using OffscreenCanvas for GPU-composited rendering. This incremental approach avoids a 'big bang' rewrite while progressively raising the visual fidelity ceiling.
6. Adaptive & Dynamic Learning Architecture
This section proposes a comprehensive adaptive learning architecture for the slide generation system, addressing the critical gap identified in Section 5.1. The architecture is based on the MAPE-K data flywheel pattern, contextual bandits for template selection, preference learning via DPO (Direct Preference Optimization), and a quality scoring engine inspired by the SlideAudit research framework. The goal is to create a self-improving system that generates progressively better slides based on user feedback and behavioral signals.
6.1 Overview: The Self-Improving Slide Engine
The adaptive learning architecture consists of five interconnected layers that form a continuous improvement loop. The Feedback Signal Collection Layer captures implicit and explicit user feedback. The Quality Scoring Engine evaluates generated slides against a multi-dimensional quality framework. The Contextual Bandit Layer optimizes template and layout selection based on accumulated feedback. The Preference Learning Layer uses DPO to align the LLM's generation preferences with user expectations. The Template Mining and Evolution Layer discovers and generates new templates from high-quality user creations and web sources.
Each layer operates at a different timescale: feedback signals are captured in real-time (milliseconds), quality scoring runs per-slide (seconds), contextual bandit updates happen per-session (minutes), preference learning runs as a batch job (hours to days), and template mining runs as a periodic crawl (weekly). This separation of timescales ensures that the system can learn and adapt without blocking the generation pipeline.
6.2 Feedback Signal Collection Layer
The foundation of adaptive learning is capturing meaningful feedback signals. Two types of signals are collected: implicit signals (derived from user behavior without explicit action) and explicit signals (direct user input). Research into user behavior analytics for presentations (DocSend, Pitch.com) provides proven frameworks for measuring engagement and effectiveness.

6.3 Quality Scoring Engine
The Quality Scoring Engine evaluates each generated slide against a multi-dimensional quality framework inspired by the SlideAudit research taxonomy (ACM 2025). SlideAudit provides the first dataset and taxonomy for automated slide evaluation with 2,400 annotated slides covering layout, typography, color, and imagery flaws. While SlideAudit's automated flaw detection currently achieves F1 scores of only 0.33-0.65 (indicating this is a hard problem), their taxonomy provides the correct evaluation dimensions.
The Quality Scoring Engine computes a composite score from five dimensions, each scored 0-1, weighted by the presentation mode and context. The composite score is stored on CompiledSlide.quality_score and feeds into the contextual bandit and preference learning layers.
The evaluation methods combine deterministic computation (contrast ratios, whitespace ratios, text density metrics) with LLM-as-judge scoring (visual impact, aesthetic appeal). Deterministic metrics run on every slide as part of the pipeline; LLM-as-judge scoring runs only for premium mode or when the composite score falls below a threshold, to control cost. The quality score is also used as a gate: slides scoring below 0.4 on any dimension are automatically flagged for re-polish, creating a quality floor.
6.4 Contextual Bandit for Template Selection
The Contextual Bandit Layer optimizes template and layout selection based on accumulated feedback using Linear Thompson Sampling. This is the highest-priority adaptive learning component because it provides immediate value with low implementation cost. The bandit treats each (layout_blueprint, design_system_mode, slide_intent) combination as an 'arm' and learns which arms produce the highest quality outcomes for different contexts.
The context vector includes: slide intent (pitch, report, educational, etc.), industry vertical, audience type (executive, technical, general), deck position (opening, content, closing), and content density (text-heavy, visual-heavy, balanced). The reward signal is a composite of: implicit feedback (edit distance inverted, retention rate, regeneration rate inverted) weighted at 0.6, explicit feedback (star rating normalized to 0-1) weighted at 0.3, and quality score from the Quality Scoring Engine weighted at 0.1.
Linear Thompson Sampling balances exploration (trying new template combinations to discover better options) and exploitation (using known-good templates for reliable results). The exploration rate starts high (0.3) and decays over time as the system accumulates data. Each bandit decision is logged with context, action, and reward for offline analysis and model improvement. The bandit model is updated after each user session, not in real-time, to avoid latency impact on the generation pipeline.
6.5 Preference Learning via DPO
Direct Preference Optimization (DPO) is the recommended approach for aligning the LLM's generation preferences with user expectations over time. Unlike RLHF (Reinforcement Learning from Human Feedback), DPO does not require a separate reward model and works directly from (chosen, rejected) preference pairs, making it more practical for production deployment. Research on DiffusionDPO and HG-DPO (CVPR 2025) demonstrates that preference optimization works for visual generation, not just text.
The preference pairs are constructed from user behavior: when a user regenerates a slide, the (original, regenerated) pair becomes a preference pair where the regenerated version is 'chosen.' When a user extensively edits a slide, the (generated, edited) pair becomes a preference pair where the edited version is 'chosen.' When a user rates slides, (high-rated, low-rated) pairs from the same context become preference pairs. These pairs are accumulated over time and used to fine-tune the DeepSeek-V3.2 model periodically (monthly for standard, weekly for premium users with sufficient data).
The key risk with preference learning is catastrophic forgetting - the model may learn new preferences at the expense of existing capabilities. To mitigate this, we recommend using a replay buffer (retain 20% of original training data in each fine-tuning batch), Mixture-of-Experts (MoE) architecture where different experts handle different style domains, and shadow deployment (run the fine-tuned model alongside the production model, compare outputs, and only promote when quality metrics improve).
6.6 Template Mining & Evolution
The Template Mining and Evolution Layer discovers and generates new layout blueprints from two sources: high-quality user creations and web-crawled presentations. This creates a self-expanding template system that grows more capable over time, learning from the best presentations available.
For user-created templates, the system analyzes slides that receive high quality scores and positive user feedback. When a user manually creates a slide layout (via the IR-Patch Edit Protocol in Phase 8) that achieves a quality score above 0.8 and receives positive feedback, the system extracts the layout pattern as a parameterized template. The parameterization captures the essential structure (grid layout, node types, relative positioning) while allowing content-specific variation. The extracted template is added to a 'community templates' pool that the contextual bandit can select for future generations.
For web-crawled templates, the system periodically crawls presentation-sharing platforms (SlideShare, Speaker Deck, Google Slides public templates) and analyzes the layout structure of high-rated presentations. The analysis extracts grid structures, content arrangements, and visual patterns that are then parameterized as layout blueprints. This requires a robust layout analysis pipeline that can handle diverse presentation formats and extract meaningful structural patterns. The SynSlideGen pipeline's annotation approach (bounding boxes, element types, text regions) provides a reference for building this analysis capability.
6.7 The MAPE-K Data Flywheel
The five adaptive learning layers form a continuous improvement loop based on the MAPE-K (Monitor-Analyze-Plan-Execute-Knowledge) pattern. This pattern is the production standard for self-improving systems and ensures that learning is structured, measurable, and safe.
The critical safety mechanism is the shadow deployment pattern: all model updates (DPO fine-tuning, bandit weight adjustments, new template additions) are first deployed alongside the production model, their outputs are compared, and only promoted when quality metrics improve on a holdout validation set. This prevents degradation from catastrophic forgetting or biased feedback signals.

7. Web Search Templates & RAG Integration
This section proposes the architecture for integrating RAG (Retrieval-Augmented Generation) and web search into the slide generation pipeline. The goal is to enable real-time content enrichment, dynamic data updates, and template auto-discovery from the web, creating a system that generates slides grounded in current, accurate information rather than relying solely on the LLM's training data.
7.1 RAG Architecture for Slide Content
The RAG pipeline runs between the writer stage and the Node Graph Builder stage (between current Stages 4.5 and 4.7 in content_pipeline.py). When the writer's output includes 'data placeholders' - markers indicating that a slide needs current data, statistics, or citations - the RAG pipeline searches for and retrieves relevant information to fill those placeholders before the Node Graph is constructed.
The architecture consists of four components: a Query Generator that transforms slide content needs into search queries, a Hybrid Retriever that combines semantic search (vector database) and keyword search (BM25) for optimal recall, a Reranker that uses a cross-encoder model to re-rank results by relevance, and a Context Injector that formats retrieved information as structured data for the writer's context. The vector database is populated with a curated corpus of reliable sources: industry reports, academic papers, news articles, and public data sets. Fresh data is indexed on a rolling 30-day window.
7.2 Web Search Template System
The Web Search Template System extends the RAG pipeline with a structured approach to finding and incorporating real-time web content into slides. Unlike generic RAG, which retrieves unstructured text, the template system uses predefined 'search templates' that know how to find, extract, and format specific types of content for specific slide layouts.
Each web search template includes: a query template with variable interpolation, a content extraction schema (what data to extract from search results), a validation schema (how to verify extracted data is current and accurate), a slide layout mapping (which layout blueprints work best for this data), and a fallback template (what to show if web search fails or returns no results). The templates are stored in a configuration database and can be extended by users or by the system's template mining process.
7.3 Real-Time Data Enrichment Pipeline
The Real-Time Data Enrichment Pipeline runs as an optional stage between the writer and the Node Graph Builder. When a user enables 'Web Enrichment' (a toggle in the frontend UI or an intent in the prompt), the pipeline processes the writer's output to identify data placeholders, executes web search templates to find current information, validates and formats the retrieved data, and injects it into the content before Node Graph construction.
The pipeline adds 1-5 seconds of latency per data placeholder (parallel searches via asyncio.gather), which is acceptable for T3 (polished tier) but too slow for T1 (instant tier). The implementation uses a two-pass approach: T1 renders with placeholder markers (e.g., '[Latest Market Data Loading...]'), and T2/T3 replace placeholders with actual data when the search completes. This ensures the < 200ms T1 target is maintained while still providing enriched content in the polished version.
Data freshness is tracked with a 'data_timestamp' field on each enriched node. When a presentation is reopened after 24+ hours, the system can optionally re-fetch data to ensure currency. This is particularly valuable for dashboards, quarterly reviews, and market analysis presentations where data currency is critical.
7.4 Template Auto-Discovery from Web
The Template Auto-Discovery system periodically crawls public presentation platforms (SlideShare, Speaker Deck, public Google Slides templates) and extracts structural patterns from high-quality presentations. This is a more sophisticated version of the user-creation template mining described in Section 6.6, applied to the broader web.
The discovery pipeline consists of five stages: Crawl (fetch public presentations), Parse (extract slide structure using the SynSlideGen annotation approach), Score (evaluate layout quality using the Quality Scoring Engine), Parameterize (extract reusable layout patterns as parameterized blueprints), and Validate (test new blueprints against the validation suite before adding to the library). This creates a self-expanding template system that continuously learns from the best presentations on the web.
The key challenge is parsing diverse presentation formats into a consistent structure. The SynSlideGen pipeline's approach of generating automated annotations (bounding boxes, element types, text regions) provides a starting point, but the system also needs to handle CSS-based presentations (from the HTML transformer), React components (from the kit JSX transformer), and engine-format presentations. A unified parsing layer that normalizes all formats to the Node Graph IR structure is essential.
8. Advanced Design System Recommendations
This section provides specific recommendations for surpassing the design quality of each reference platform. The recommendations are grounded in the competitive analysis and focus on actionable improvements to Plan v2's architecture that would elevate the output quality above all four reference platforms.
8.1 Surpassing Dokie.ai: Design Intelligence
Dokie.ai's strength is structured, business-appropriate content generation with clean formatting. To surpass this, Plan v2 needs to match Dokie.ai's content structuring quality while adding superior visual design. The key improvements are: (1) multi-format input support (PDF-to-slides, Word-to-PPT, Excel-to-slides, URL-to-slides) which Plan v2 currently lacks, (2) content-aware layout selection that analyzes the semantic structure of input content and maps it to optimal layout blueprints, and (3) intelligent content density management that ensures each slide has the right amount of information - not too sparse, not too dense.
The multi-format input feature requires a pre-processing pipeline that runs before the writer: a Document Parser that extracts structured content from PDFs, Word documents, Excel spreadsheets, and web pages; a Content Analyzer that identifies the semantic structure (headings, data points, narratives, visuals); and a Slide Planner that maps the analyzed content to an optimal slide sequence with appropriate layout blueprints. This pipeline should be added as a pre-Phase 1 stage or as an extension to the existing skeleton planner.
8.2 Surpassing Chronicle HQ: Interactive Widgets
Chronicle HQ's motion-ready widgets are the most innovative feature in the market. To surpass this, Plan v2 needs first-class support for interactive elements in the Node Graph IR, the design system, and all four render targets. The proposed architecture adds an 'interactive' node type to SlideNode with subtypes: hover-card (tooltip or expanded content on hover), animated-chart (bar/line/pie charts with animated data entry), embedded-video (inline video player with custom controls), click-reveal (content that appears on click), scroll-timeline (horizontal scroll through a timeline), and live-data (real-time data from an API endpoint).
Each interactive widget is defined by: a widget schema (data structure, interaction model, visual states), a widget renderer (per-target rendering logic), a widget style (mapped from the design system), and a widget behavior (animation timing, interaction responses, accessibility alternatives). The widget system should be extensible via a plugin architecture similar to Bespoke.js, allowing third-party developers to create custom widget types that integrate with the Node Graph IR.
8.3 Surpassing Canva Pro: Brand Intelligence
Canva's Brand Kit is the gold standard for design system enforcement at scale. To surpass this, Plan v2 needs a Brand Intelligence system that goes beyond static brand guidelines to actively enforce and evolve brand identity across presentations. The proposed Brand Kit is a persistent, cross-deck design system that includes: brand colors (primary, secondary, accent, neutral palette with accessibility-verified contrast pairs), brand typography (display, heading, body, caption fonts with size scales and line heights), brand imagery (approved photos, illustrations, icons with style guidelines), brand voice (tone, formality level, terminology preferences for AI text generation), and brand layout rules (spacing grid, margin rules, element placement preferences).
The Brand Intelligence layer extends the Brand Kit with learning capabilities: it tracks which brand variations users prefer (A/B testing within brand guidelines), learns which design choices are most effective for specific audiences (using the adaptive learning feedback signals), and suggests brand guideline refinements based on accumulated usage data. This creates a 'living brand kit' that evolves with the brand rather than remaining static, which is a genuine differentiator over Canva's static Brand Kit.
8.4 Surpassing Figma Slides: Pixel-Perfect IR
Figma's pixel-level design control comes from its custom GPU rendering pipeline and Design Mode that exposes the full component/variable system. To surpass this, Plan v2 needs to offer similar pixel-level control through the Node Graph IR while maintaining the AI-first generation approach. The proposed 'Design Mode' is a power-user interface that renders the Node Graph IR visually using tldraw's Editor + Store pattern, allowing direct manipulation of nodes, edges, geometry, and style properties.
Design Mode should support: drag-to-reposition (mutates node.geometry.grid_placement and offset_x/y), resize handles (mutates node.geometry dimensions), style editing panel (mutates node.style tokens and custom_overrides), layout swap (mutates all nodes' grid_placement based on a new blueprint), and direct property editing (mutates any node property). All edits go through the IR-patch protocol, ensuring that Design Mode edits are deterministic, undoable, and re-renderable across all four targets. The key advantage over Figma is that Plan v2's Design Mode edits remain AI-editable - a user can manually adjust a node and then ask the AI to 'make this pop,' and the AI works with the edited IR, not against it.
8.5 The Unified Differentiator: Design-to-IR Pipeline
The ultimate differentiator that Plan v2 can achieve - which none of the four reference platforms offer - is a unified Design-to-IR pipeline that allows any visual design to be reverse-engineered into the Node Graph IR, making it AI-editable, design-system-constrained, and multi-target renderable. This means a user can upload a Figma design, a Canva template, a PowerPoint slide, or a screenshot of any presentation, and the system extracts the Node Graph IR, applies the current design system, and makes the design fully editable and AI-improvable.
This reverse-engineering pipeline consists of: an Image Analyzer (VLM model that describes the visual structure of a slide image), a Structure Extractor (maps the visual description to a Node Graph IR with geometry), a Style Mapper (maps visual styles to design system tokens), and a Validation Gate (ensures the extracted IR produces a visually similar result when rendered). This pipeline effectively makes any visual design a first-class citizen in the Plan v2 ecosystem, which is a capability that no competitor currently offers.
